# Microservices QA Portfolio
Quality Engineering portfolio demonstrating microservices testing with Java, RestAssured, Pact and GitHub Actions CI/CD

## Services

| Service | Port | Role |
|---|---|---|
| `order-service` | 8081 | Consumer — calls ProductService and UserService |
| `product-service` | 8082 | Provider — `/products` |
| `user-service` | 8083 | Provider — `/users` |

## Contract testing with Pact

`order-service` is the consumer of `product-service` and `user-service`. Consumer-driven
contracts are generated by JUnit 5 Pact tests, published to a Pact Broker, and verified by
each provider against every contract published for it — no shared test environment or
manually coordinated end-to-end suite required.

```
order-service (consumer)                 pact-broker                product-service (provider)
        │  mvn test                           │                              │
        ├─ generates target/pacts/*.json      │                              │
        │  mvn pact:publish ──────────────────►                              │
        │                                     │                              │
        │                                     │◄── mvn verify (pulls pacts) ─┤
        │                                     │◄── publishes verification ───┤
        │                                     │                              │
        │                          can-i-deploy checks broker for a          │
        │                          successful, matching verification         │
```

### Run it locally

1. Start the broker:
   ```
   docker compose up -d
   ```
   Broker UI: http://localhost:9292 (basic auth `pact` / `pact`).

2. Generate and publish the consumer contracts:
   ```
   cd order-service
   ./mvnw clean test                              # writes target/pacts/*.json
   ./mvnw pact:publish -Dpact.consumer.version=0.0.1-local1
   ```

3. Verify each provider against the broker:
   ```
   cd product-service
   ./mvnw clean verify -Dpact.provider.version=0.0.1-local1 -Dpact.verifier.publishResults=true

   cd ../user-service
   ./mvnw clean verify -Dpact.provider.version=0.0.1-local1 -Dpact.verifier.publishResults=true
   ```
   `verify` (not `test`) runs the `*ProviderIT` classes via maven-failsafe, so plain
   `mvn test` still passes without a broker running.

4. Check whether it's safe to deploy:
   ```
   docker run --rm --network host pactfoundation/pact-cli:latest \
     broker can-i-deploy \
     --broker-base-url http://localhost:9292 --broker-username pact --broker-password pact \
     --pacticipant OrderService --version 0.0.1-local1 \
     --pacticipant ProductService --version 0.0.1-local1 \
     --pacticipant UserService --version 0.0.1-local1
   ```

### How it's wired

- **Consumer side** (`order-service`): `ProductServicePactTest` / `UserServicePactTest` define
  expected interactions with `PactDslWithProvider`, run against a Pact mock server, and write
  pact files to `target/pacts/`. The `au.com.dius.pact.provider:maven` plugin's `pact:publish`
  goal pushes them to the broker, tagged with the branch/version.
- **Provider side** (`product-service`, `user-service`): `ProductServiceProviderIT` /
  `UserServiceProviderIT` use `@PactBroker` to pull every contract published for that provider
  and replay each interaction against a real running Spring Boot instance
  (`@SpringBootTest(webEnvironment = RANDOM_PORT)`). `@State` methods set up any fixture data
  a contract's `given(...)` clause requires. Results are published back to the broker with
  `-Dpact.verifier.publishResults=true`.
- **Deployment gate**: `can-i-deploy` asks the broker whether every provider has a *successful*
  verification for the exact consumer/provider versions being deployed — the mechanism that
  replaces a slow, shared end-to-end environment.

### CI

`.github/workflows/product-service-ci.yml` runs each service's unit/component tests, then a
`pact-contract-testing` job that spins up Postgres + Pact Broker as service containers,
publishes contracts, verifies both providers, and runs `can-i-deploy` — all keyed off
`github.sha` so every result is traceable to the exact commit.
